# Shared project workspace

This is the shared starting point for people and any coding agent. It records
where the durable project state lives, how to refresh it, and how to keep work
from being stranded in local worktrees.

## Start here

1. Read the status hub at `specs/artifacts/project-status/README.md` for the
   current ChartSearchAI, Catalyst, pull-request, evidence, and decision
   inventory.
2. Read the product authority named by the relevant effort before changing
   behavior. For Catalyst, the Feature 008 plan and tasks define delivery order
   and progress; the product specification and binding design define behavior,
   while the program roadmap retains evaluation and broader-conversation
   decisions. For ChartSearchAI, use the dual-provider roadmap, its status,
   upstream inventory, and conformance contract named in `AGENTS.md`.
3. Refresh changing facts and generated views with
   `scripts/project-status.sh refresh`. Run
   `scripts/project-status.sh github` first when GitHub pull-request state may
   have changed. It prints the exact live collection commands; reconcile their
   output into `pull-requests.json` before regenerating.

## What is durable

The editable status source is `specs/artifacts/project-status/*.json`.
Markdown tables and CSV files beside it are generated by `render.py`. The
dashboard is a browser for those same files, built from `site/status/`; it does
not create another roadmap or save browser edits.

GitHub pull requests, commits, checks, versioned specifications, and recorded
run artifacts establish claims. Codex and Claude conversations provide useful
investigation history, but they are supporting evidence only. Record any
decision, revision, acceptance result, or next action in the status source or
the applicable product authority before ending a work session.

## Browse the dashboard

After this branch reaches `main`, GitHub Pages publishes the dashboard at
`https://pmanko.github.io/clinical-ai-validation-harness/status/`. For a local
browser session, run `npm --prefix site run status:dev`. The former private
Sites deployment is retained only as a legacy snapshot while the GitHub Pages
build replaces it; do not publish new status versions through Sites.

## Worktree rules

Use one clean worktree for each active code pull request. A local change must
be committed to an existing review branch, moved into a named patch with a
specific follow-up, or removed after triage. Before removing a worktree,
record its outcome in `specs/artifacts/project-status/evidence/` and make sure
any useful change has a tested destination.

`scripts/project-status.sh worktrees` shows the registered worktrees and
prunable entries. `scripts/project-status.sh prune-worktrees` removes only
registrations whose directories are already missing; it never removes a
working directory. Remove a dirty worktree only after its changes have been
triaged.
