# Catalyst Iterative Workbench UX Audit — 2026-07-18

## Outcome

The active-session page is a sequence of individually functional sections, not
one iterative workspace. The next UI pass should preserve exactly one canonical
SQL editor and exactly one reusable natural-language composer. The composer is
the initial `Ask OpenELIS` input before a session exists and becomes the
`Refine Query vN` input after generation; the disabled copy of the initial form
must disappear once its question is present in history.

The active-session workspace should be organized around:

1. a compact chronological session history;
2. the one SQL editor with adjacent Format, Validate, and Run controls;
3. bounded Results / Validation / Evidence panes; and
4. a bottom workbench dock whose compact rail remains reachable while browsing
   results and whose expanded state contains the one reusable Ask/Refine
   composer.

The dock must expose its grounding state, for example:

`Based on Query v5 · Run 3 · 49 rows · execution summary attached`

or:

`Based on edited SQL · displayed results are stale · run to attach execution context`

This is a UX consolidation, not a second floating SQL editor and not a chat UI
that hides the query artifact.

## Live audit evidence

The inspected restored session was approximately 7,859 CSS pixels tall in a
766 × 935 viewport:

| Surface | Approximate document position |
|---|---:|
| Initial disabled question | 629 px |
| Follow-up composer | 1,476 px |
| SQL editor | 1,913 px |
| Parameters | 2,252 px |
| Validation | 2,929 px |
| Results start | 3,260 px |
| Generation evidence | 5,491 px |
| Version history | 6,768 px |

The current sticky banner can jump to the follow-up input, but it cannot keep
the SQL editor, Validate/Run actions, results, and follow-up context together.
The page also contains three competing text surfaces during an active session:
the disabled initial question, the follow-up instruction, and the SQL editor.
Only the last two should remain, and each should have one clear job.

## Recommended interaction model

### Before a session

- Show the queryable schema guide and one `Ask OpenELIS` composer.
- Keep example questions absent.
- On generation, retain the question as turn 1 and transform the same composer
  into the active-session Refine composer.

### During a session

- Put compact chronological turns above or beside the work area. Earlier turns
  are collapsed; the latest may be expanded. A summary includes instruction,
  resulting query version, manual/model state, execution row count, and failure
  state. UUIDs, digests, prompts, and raw evidence stay under Details.
- Keep one CodeMirror SQL editor. Put Format, Validate, and Run adjacent to it;
  do not make the user scroll through parameters and validation to reach Run.
- Bound the results viewport with its own scrolling and sticky header so a
  49- or 100-row result does not create several pages of document scroll.
- Keep a compact bottom dock visible on desktop. It shows current query,
  validation, execution/staleness, and actions. Expanding `Edit SQL` reveals the
  same editor; expanding `Ask follow-up` reveals the same composer.
- After generation, focus/reveal the SQL editor. After Run, announce and focus
  the results heading while leaving the dock reachable. A dirty edit immediately
  marks previous results stale and changes the grounding label.
- `New session`, provenance, raw evidence, and full version history are
  secondary details rather than permanent full-height sections.

Microsoft SSMS grounds a dockable assistant on the active query editor,
connection, result grid, messages, and conversation history; Hex similarly keeps
its notebook agent attached to the notebook artifact and preserves thread
history. These are useful patterns, not visual templates:
[SSMS context](https://learn.microsoft.com/en-us/ssms/github-copilot/chat-context),
[SSMS dockable chat](https://learn.microsoft.com/en-us/ssms/copilot/copilot-in-ssms-chat),
[Hex Notebook Agent](https://learn.hex.tech/docs/explore-data/notebook-view/notebook-agent).

## Execution-grounding boundary

The current Gateway already includes the latest matching-digest execution's
status, result column schema, row count, duration, and database diagnostic in a
follow-up. It does not include returned row values. After a dirty editor change,
the old execution no longer matches and is correctly omitted.

The immediate UX pass should make this behavior visible and truthful. It must
not claim that the model can inspect displayed values when only an execution
summary is attached.

Value-level follow-ups are a separate contract decision. If required, the
smallest explicit design is a removable attachment such as
`Results from Query v5 · rows 1–25`, carrying a bounded deterministic row sample,
digest, execution/version reference, and provenance. It must never silently send
the entire result set. This decision remains at the user checkpoint because it
reverses G2.8's approved exclusion of result rows.

## Queryable-schema audit

“Know what to ask” currently calls dataset-overview and record-browser endpoints.
It never renders the already-fetched editor catalog, so it cannot tell a user
which SQL relation or column names are valid.

There are also three different meanings of “available”:

1. **Current supported model/editor catalog:** one approved view,
   `analytics.lab_result_fact_v1`, but only 8 named fields.
2. **Live physical approved view:** the same view has 16 columns.
3. **Database-role-accessible surface:** the read-only role can SELECT seven
   business relations, including low-level public projections and pipeline
   metadata. Manual Run is advisory and therefore can reach this broader surface.

The live fact-view columns are:

| Column | PostgreSQL type |
|---|---|
| `observation_id` | `varchar` |
| `patient_id` | `varchar` |
| `service_request_id` | `varchar` |
| `specimen_id` | `varchar` |
| `result_status` | `varchar` |
| `observed_at` | `timestamptz` |
| `issued_at` | `timestamptz` |
| `test_code_system` | `varchar` |
| `test_code` | `varchar` |
| `test_name` | `varchar` |
| `result_value` | `numeric` |
| `result_unit` | `varchar` |
| `result_unit_system` | `varchar` |
| `result_unit_code` | `varchar` |
| `specimen_received_at` | `timestamptz` |
| `receipt_to_release_minutes` | `numeric` |

**Superseded on 2026-08-25:** the single-view recommendation below was an audit
proposal, not the chosen product boundary. The current decision is that every
relation readable by the configured read-only database role is available to
both model and human paths. Reviewed descriptions improve guidance but never
hide a readable relation. The historical 16-column mismatch remains useful
evidence that catalog metadata must describe the database truthfully.

The existing `GET /v1/catalyst/workbench/catalog` should remain the single
source for model grounding, completion, and the user-facing explorer. A v2
response should add:

- view qualified name, kind, grain, and description;
- every supported column's logical/database type, nullability, description, and
  unit relationship when applicable;
- truthful execution capabilities: read-only SELECT, advisory validation,
  current maximum returned rows, and statement timeout; and
- cataloged semantic values labelled as available values, not example prompts.

The raw catalog's 1,000-row constraint conflicts with the live 100-row runtime
cap, its 366-day/allowed-filter language is not enforced, and its demo/synthetic
classification does not generalize to a real deployment. Those fields must be
corrected or presented as recommendations rather than enforced facts.

The schema guide should be compact and searchable, expand the sole supported
view by default, and show name, type, nullable state, and plain-language meaning.
The existing record preview becomes a secondary disclosure. Hex's data browser
is a useful reference because it searches schema/table/column metadata, exposes
types and descriptions, previews rows, and offers qualified-name actions:
[Hex Data Browser](https://learn.hex.tech/docs/explore-data/data-browser).

## Responsive and accessibility rules

- At narrow widths or high zoom, pin only the compact dock rail. Expanded SQL or
  composer content becomes a bounded in-flow panel or bottom sheet with its own
  scroll; it must not permanently cover results or the software keyboard.
- Reserve page space for the dock and verify that every focused control remains
  unobscured. Sticky UI must be disabled or reduced in short viewports.
- Preserve visible focus, native disclosure semantics, keyboard ordering, a
  polite chronological `log`, and status announcements for generation, Run,
  result counts, and stale state.
- Reflow ordinary content at 320 CSS px. SQL and result grids may use labelled
  two-dimensional scrolling.

Relevant accessibility guidance:
[WCAG sticky footer technique C34](https://www.w3.org/WAI/WCAG22/Techniques/css/C34),
[Focus Not Obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html),
[Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), and
[ARIA log](https://www.w3.org/WAI/WCAG22/Techniques/aria/ARIA23.html).

## G2.9 acceptance checkpoint

Automated and live checks must prove:

1. an active session has one SQL editor and one Ask/Refine composer, with no
   disabled duplicate initial question;
2. the compact dock remains reachable through long results and never obscures
   keyboard focus at desktop, 390 × 844, 320 CSS px reflow, or 200% text;
3. edit → stale result → Validate/Run → matching execution context → Refine is
   visible as one continuous workflow;
4. dirty and unexecuted states truthfully say that prior execution context is
   omitted;
5. refresh restores dock state, editor, chronology, execution, and grounding;
6. the schema guide shows every relation and column readable by the configured
   read-only role;
7. the runtime catalog, SQL completion, model request, and schema guide use the
   same versioned catalog response; and
8. live information-schema checks prove that refreshed catalog contents match
   what that role can currently read.

No branching, multiple editors, or silent result-row sharing is part of this
pass. The data-boundary wording above was corrected on 2026-08-25; the earlier
single-view recommendation is superseded.
