# Direct Load Profile

**Engine**: stdlib + PyMySQL. **Implementation**: `harness/load/`.
**Scope**: deterministic corpus build and evidence, pending external reusable
data-tooling ownership. Target preparation, deployment and restoration are external.

## Data flow

```text
legacy_27_raw -> SQLMesh -> physical versioned snapshots
                         -> direct SQL copy -> disposable OpenMRS build schema
                         -> portable module-clean dump + provenance
                         -> deploying owner restores a fresh target
```

SQLMesh's logical views are not portable clinical data dumps. Resolve each view
to its physical snapshot, then copy into an existing caller-prepared build schema
using only OpenMRS-defined columns. No service startup, process restart or live
schema promotion is part of this operation.

## Loader contract

- `pipeline.py` enumerates `LoadResource(sqlmesh_view, target_table, primary_key,
  write_disposition)` in FK dependency order; parent orders precede typed children.
- `snapshot_resolver.py` resolves logical views to physical SQLMesh snapshot names.
- `loader.py` projects the intersection of destination/source columns. Fields
  absent from the target are reported; fields absent from source use target defaults.
- `replace` means TRUNCATE + INSERT for canonical clinical history; `merge` means
  INSERT IGNORE for compatible baseline lookup rows; `append` means INSERT.
- CIEL concept tables remain baseline-owned, not copied over with source dictionary
  rows. FK reconciliation uses reviewed seed maps and explicit collision decisions.
- Non-strict legacy-date handling, UTC and FK-check settings are explicit;
  post-copy FK and completeness evidence must surface specific offending records.
- The loader copies rows, never DDL or module Liquibase state. OpenMRS owns schema
  changes and module initialization. Do not change a running deployment in place.

## Portable data handoff

A deterministic dump contains reviewed clinical/core data with module-owned tables
and module Liquibase entries excluded as required by the accepted policy. The
receiving OpenMRS app initializes its modules on a fresh restored database.
Version/checksum receipts identify the delivered bytes, mappings and source corpus.
The umbrella/product deployment workflow owns packaging operations, restoration,
service lifecycle, reindexing and environment cleanup; this contract does not
prescribe harness Makefile/Compose entry points.

## Conformance and evidence

Use a caller-prepared disposable database and the selected module's CLI help.
Verify post-load rows/content against SQLMesh audit floors; test repeated identical
loads for normalized content equality. Emit FK/completeness findings, dropped-column
rationale and per-table counts/content checksums. Query prepared REST/FHIR endpoints
for patient-level smoke and translation-coverage checks. Counts alone are not
clinical-preservation evidence. Any unresolved clinical/FK failure blocks acceptance.

The corpus build must not be mistaken for product or deployment acceptance.
External startup/test receipts are separately attributed, not generated by runner
checkout/build commands. No Git revision or source tree is required to collect
record-level readback evidence.
