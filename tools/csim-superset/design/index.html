Validation results

The local and published full dashboards each pass 91 chart-data requests with assertions: all 21 charts in Month, Quarter and Year, plus expected values, date boundaries, filter changes and cleared selections.

  • Expected examples include Q1 at 10% for hospital 91, a February gap, March at zero, and April with no eligible denominator.
  • Partial first and last periods remain visible. Overall measures respect the selected dates. Existing hospital-comparison calculations are retained.
  • The two all-time total cards retain their intentional date-filter exclusions. A future calendar period does not change the newest-data card.
  • Native ZIP import also passes in an independent instance with different chart identifiers. The open issues below distinguish remaining enhancements from checks needed for production.

The underlying reporting need

For my hospital or a comparison cohort, show the results for a chosen care location and date range. Let me switch between monthly, quarterly and annual views, while keeping the selected population, reporting window and calculation rules clear.
  1. Predictable filters across chartsA selection affects the intended charts. Any charts that deliberately show a different population or benchmark are clear to the reader.
  2. Separate the date range from the groupingChoosing Quarter groups the selected records. It must not silently expand February–March into a full January–March reporting window.
  3. Time choices and labels that fit the dataMonthly submissions need meaningful grouping choices, chronological order, and labels such as “Nov 2025”, “Q1 2026” and “2026”.
  4. Missing data stays visibleA month without submissions remains visible. It is distinct from a valid zero and from a rate that cannot be calculated.
  5. Defined calculations at every levelA quarterly rate or a multi-hospital comparison follows an agreed rule. Changing the grouping must not quietly substitute a maximum or an average.
  6. The same behavior after publicationMoving a tested dashboard to production preserves its datasets, measures, chart relationships and filter coverage.

In Power BI terms, these span slicers and their visual interactions, the date table, measures, and deployment. For CSiM, the equivalent Superset settings must work together across the saved dashboard.

Filters do not consistently affect the expected charts

Hospital, care location, date range and time unit need to work together. The main selector covers trends and overall charts; separate selectors cover paired comparisons. Saved chart references and conflicting selector coverage can cause a chart to use different records from those the user expects.

The two submission-total cards deliberately show all-time totals, while location breakdowns deliberately show all care locations. Those exceptions need to stay clear.

Dates need appropriate labels, ordering and grouping

Default labels can mix years, months and weekdays. A fixed Month–Year format does not adapt to quarters or years. A formatted text field can also sort alphabetically.

The development trends also aggregate precomputed monthly rates with a maximum. A quarter can therefore show its highest monthly rate instead of a rate calculated for the selected months.

A label made from existing records cannot supply a month with no records. Missing submissions, a measured zero and a rate with no qualifying denominator need distinct treatment.

2. Solutions demonstrated in the dashboard

These corrections are implemented across the 21-chart demo. Each explanation links to a recorded workflow with checked results.

What the solutions require

Dataset solution

Keep real dates and a complete calendar

Changing a date into a label does not create missing periods. A calendar supplies the months, quarters or years that have no records. The selected date range applies to actual observations before they are grouped.

The demo keeps the reporting date, period label and ordering separate. A missing month, a valid zero and a rate with no eligible denominator remain distinct.

See dates and missing periods →

Chart solution

Match the labels to the grouping

The full dashboard uses labels such as 2025-11, 2026 Q1 and 2026. They remain chronological when Superset reorders a comparison chart’s text axis.

Changing Month → Quarter → Year changes the labels and calculated values together. Friendly month-name labels are addressed in the open issues below.

See the three groupings →

Dashboard solution

Define what each filter controls

Main hospital trends, separate hospital/cohort comparisons, location breakdowns and all-time totals have different scopes. Those relationships must be saved with the dashboard and checked after import.

The demo tests selection changes and prevents empty required selections from combining overlapping totals. Intended exceptions are listed in the chart-coverage table.

See filter selections →

Calculation solution

Group the selected records before calculating

Choosing Quarter should calculate the rate for the selected months, rather than take the highest monthly percentage. A February–March selection must not add January just because the label is Q1.

The corrected dataset applies the date range first, then groups the records and calculates the period’s values.

Fix demonstrated · newer Superset build

Save allowed time units with each control

This fix runs in the separate, newer Superset installation. CSiM offers Month, Quarter and Year; the hourly example offers Hour, Day and Week. Each control has its own saved list. Changing a selection updates its charts without changing the other dashboard’s available units.

Superset stores these choices with the dashboard’s filter definition. The demo checks the menus after reload and native export/import, along with Q1 at 10% and two daily specimen totals of 72.

Authoring and implementation

In the upstream filter editor, use “Pre-filter available values” for the Time Unit control and select its allowed units. Choose a saved default from that list. The snapshot keeps the instance’s full set of time units available.

The native setting is time_grains. The tested build is upstream commit e22ce19. Its virtual dataset SQL uses get_time_filter for the reporting window and explicit three-month quarter intervals. These are dataset changes; the Superset image is an upstream build.

3. Unresolved issues and proposed solutions

The date, gap and filter corrections above work in the demo. The following items concern release availability, optional presentation improvements and deployment to the CSiM installation.

Time Unit · Stable-release availability

Use per-dashboard time choices in a released version

What works: the upstream snapshot demonstrates independent choices on two dashboards, including saved defaults and native import.

What remains: this feature is not in stable Superset 6.1.0 or a newer published preview release. The 6.1.0 demo still restricts Month, Quarter and Year across its entire Superset instance.

Proposed approach: test the snapshot alongside 6.1.0, then adopt a stable release containing the feature when available. An earlier rollout would mean maintaining and testing a build with the upstream change.

Watch the per-dashboard fix in newer Superset → · Watch the shared-list workaround in 6.1.0 →

Upstream changes and build version

Per-filter time choices and a follow-up correction are merged into the development branch. The snapshot is pinned by commit and image digest; it does not track a moving Docker tag.

The control keeps an already selected value visible even if the allowed list changes. Set a valid default when editing the list, and check saved or shared filter selections during rollout.

Date presentation · Optional enhancement

Use “Nov 2025” without losing chronological order

What works now: 2025-11, 2026 Q1 and 2026 sort correctly and change with the time unit.

Proposed solution if month names are required: keep a separate date value for ordering and format only its displayed label. Superset’s comparison-chart renderer needs to preserve that distinction. Extend and test the renderer across line and stacked charts, including multiple series and missing periods. Keeping the current sortable labels requires no additional change.

Dashboard transfer · Partly addressed

Repair every saved reference and verify the destination

What works now: all 21 charts load after native import with changed identifiers. Dataset SQL, filter defaults and exclusions match, and the recorded Month/Quarter interactions work.

What remains: Superset 6.1.0 leaves old identifiers in all six cached filter-scope lists and the global list. The existing workflow can pass despite that metadata defect. Newer upstream code includes a repair, but its remapping still needs a test in which chart identifiers change.

Proposed next step: verify that repair, then test the bundle against a copy of the destination configuration, including saved links and updates to shared objects. The development training dashboard shares 20 charts. The CSiM production and WordPress routes need their own checks.

Import details

The successful check covers UUID relationships, exact SQL, saved defaults and scope.excluded. It reports chartsInScope cache mismatches separately. Checking only whether an identifier exists is insufficient: an old identifier can now belong to a different chart.

The upstream import repair and additional scope remapping address this defect. Pin the dashboard files and Superset build together, and check updates to existing objects as well as fresh imports.

Other client reports and what this demo covers

Already specified or marked fixed by the team: hospital-only and cohort/state-only menus, several default selections, whole-percent axes and much of the dashboard wording. The demo retains or adapts these and checks them; they are not all new fixes.

Still requiring a targeted check: the intermittent cohort-only/permalink problem, embedded WordPress navigation and access, production section links and historical-data completeness. A successful standalone dashboard does not establish those outcomes.

Reporting choices to confirm: the main versus secondary hospital selector for the submission card, and the cohort-only starting view. The demo starts with hospital 91 plus Cohort and returns no results after Clear all. Its newest-data card shows the latest observation month, not the time of import or dashboard update.

The client issue responses, reporting requirements and detailed coverage provide the supporting context.

Additional reporting definitions that need agreement

ASB prevalence and treatment labels use different denominators from the current dataset SQL. The demo retains those formulas and identifies the discrepancy beside the measures.

Proposed next step: confirm the intended numerator and denominator with the dashboard owners, then update the definition text, SQL and expected examples together. This is distinct from the period-grouping correction already demonstrated.

Restore archive: the CSiM backup folder contains an April 2026 dashboard ZIP, dataset/chart SQL and styling. The dashboard tutorial identifies the ZIP as the primary restore artifact. It contains definitions; source data, accounts and server configuration are separate.

Technical approach and operational context

The full synthetic version applies the selected date range to source records before grouping them into months, quarters or years. The existing hospital and cohort calculations then operate on those groups. Calendar rows preserve absent periods, and separate sort and label fields control the axis.

Superset can also apply an outer date predicate. A dedicated filter column keeps that predicate inside the selected range, so a quarter that starts before the range is not discarded. Actual reporting dates and period labels remain separate.

Chart references are mapped to the destination identifiers. Hospital and comparison filter choices use PostgreSQL-compatible expressions. The newest-data card uses actual observations and excludes the two secondary hospital selectors.

The development host runs Superset 6.1.0 and also hosts unrelated services. Its app health check refers to a missing script; the web endpoint responds despite the unhealthy container label. Its deployment configuration has local changes beyond the GitHub revision. The production installation is separate from this synthetic demonstration.

Implications for Catalyst and other dashboard outputs

A reusable dataset needs its SQL and measure definitions. A widget needs its data, calculation and display settings. A dashboard also needs the arrangement, filter coverage and deliberate exceptions. Those relationships matter when a design changes or moves to another tool.

For Catalyst’s Workbench and Library, these are concrete review criteria: save the SQL with the dataset, keep dataset/widget/dashboard relationships visible, and check the dashboard after a turn changes any of them. Tool-specific prompts or agents can help author the output; they still need the same reporting contract and validation examples.

The Superset demo is separate from Catalyst product implementation. Metabase and Evidence remain alternative output candidates, not implemented integrations described by this page.
