# OpenMRS HIV/ART data source

The second data source registered with Catalyst (alongside OpenELIS
Laboratory): OpenMRS's demo HIV/ART program data, ingested via
fhir-data-pipes from the OpenMRS FHIR2 R4 endpoint into its own
`catalyst_analytics_hiv` database.

## Layout

- `config/` — fhir-data-pipes controller config (`application.yaml`,
  `flink-conf.yaml`), the ViewDefinitions under `views/` (upstream defaults
  plus documented additive extensions and gap-fill views), and
  `postgres-sink.json` pointing at `catalyst_analytics_hiv`.
- `sql/` — the curation layer over the lossless default views:
  `001_analytics_hiv_v1.sql` (fact/dimension views, comments as catalog
  input), `002_analytics_hiv_comments_v1.sql`.
- `catalog-overlay.json` — the one hand-maintained input to catalog
  generation (identity, approved views, semantic canonicals); see
  `analytics/catalog-overlay.json` in the `targets/catalyst` submodule for
  the layering rule this follows.
- `catalog/openmrs-hiv-catalog.json` — GENERATED by
  `scripts/generate-catalyst-source-catalog.py`; do not hand-edit.
- `data-sources.json` — the `CATALYST_DATA_SOURCES_PATH` registry entry the
  gateway container mounts (`catalogPath` here is the in-container path;
  `compose/catalyst-mvp-isolated.override.yml` mounts the matching host file).
- `run-ingestion.sh` — one-shot runbook: ingest -> apply curated SQL ->
  register the pipeline run -> regenerate the catalog. See the script header
  for prerequisites (the isolated stack up, OpenMRS reachable, host awake).

## Test coverage

- `tests/test_hiv_fact_view_semantics.py` (harness root) executes
  `sql/001_analytics_hiv_v1.sql` against a scratch PostgreSQL and asserts the
  view semantics: per-coding collapse, CIEL/SNOMED/WHO-ANC pivot, the
  patient-join exclusion, and the visit-fact date-window/gap computation.
- **No gold execution-match fixture coverage yet.** T094's gold
  execution-match spot checks (`evals/fixtures/catalyst-notebook-golden/`)
  target the OpenELIS source's `analytics.lab_result_fact_v1` /
  `public.service_request_flat_v1` shapes only. Adding HIV-specific golden
  scenarios is tracked as follow-up work, not implied by this source's
  presence in the registry.

## Merge-order / back-compat contract

The harness pins `targets/catalyst` to a specific submodule commit
(`git submodule status`). Because this source's registry entry
(`data-sources.json`) and compose wiring live in the harness, and the
gateway/UI code that consumes them lives in the `targets/catalyst`
submodule:

1. **`targets/catalyst` merges first** — its `feat/multi-dataset` branch
   must land (or at least be pushed and reachable) before the harness
   re-pins to a commit on it; pinning to an unpushed/unmerged commit leaves
   a fresh clone unable to resolve the submodule.
2. **The harness merges second**, bumping the submodule pin in the same
   commit that adds/updates this source directory and the compose override.
3. Draft PR descriptions for both sides are kept in
   `specs/artifacts/planning/multi-source-pr-contracts.md` for use when
   actually opening them.

This order is not yet executed — both repos currently only have local
commits on their feature branches. Pushing and opening PRs is a deliberate,
separate step the user triggers explicitly.
