Project overview

A framework for orchestrating and evaluating open models in clinical workflows.

Open Clinical AI is an open framework for orchestrating small, open-weight language models against clinical, administrative, and surveillance workflows, and for evaluating the resulting evidence. It combines staged model calls with visible source context, explicit execution, and reviewable results. ChartSearchAI and Catalyst are its example implementations, in OpenMRS and OpenELIS.

Because the models run locally via llama.cpp — no cloud APIs — the same framework fits health systems where connectivity, compute, cost, or data-privacy rules make cloud AI unavailable, without changing the architecture.

Local by design

Runs entirely on local hardware via llama.cpp — no cloud APIs. Patient data never leaves the deployment.

Answer checks

Each product keeps its checks visible: staged model calls, temporal and structure findings, citation resolution, advisory SQL findings, and explicit execution.

Published evidence

Published reports retain the inputs, outputs, source evidence, and review method needed to interpret a result. Catalyst will publish a fresh comparison after its generic connection and Spark reference deployment are accepted.

Med Agent Hub

How each answer is produced.

ChartSearchAI owns the OpenMRS workflow and can execute it through either its bundled provider or a configured Med Agent Hub provider. The recording uses Hub; the five stages below are the shared lifecycle shown in the demo above.

1 Context

Load patient records and source provenance.

2 Answer

Generate the initial answer with the selected profile.

3 Check

Apply deterministic temporal and output rules.

4 Evidence

Resolve citations and record grounding results.

5 In-Depth

Generate additional detail from the checked answer.

OpenELIS reporting · In progress

Four ways from laboratory records to a dashboard.

Start with a report you already know, or ask a new question. These pathways serve different needs: they are complementary choices, not equivalent alternatives to rank. OpenELIS reporting works independently of Catalyst and AI.

Path 1 · Export and visualize

Use a familiar OpenELIS report

OpenELIS report builder → CSV → Superset

Choose fields and filters, generate a CSV, then upload it into Superset to build a table, chart and dashboard. No Catalyst or AI step is required.

Data: a snapshot for the selected reporting period. Export and upload again when you need a new snapshot.

Path 2 · Bring your report

Build on a CSV in Catalyst

OpenELIS report builder → CSV → Catalyst → Superset

Upload the report, review its columns and types, and save a Dataset. Create charts, arrange a dashboard and publish it to Superset without writing SQL.

Data: an imported snapshot with a saved version. A later file does not silently replace an existing published report.

Path 3 · Ask the database

Explore OpenELIS directly

OpenELIS PostgreSQL → Catalyst → Superset

Browse available data, ask and refine a question, review the proposed SQL and choose when to run it. Save the result as a Dataset, then build and publish a dashboard.

Data: queried from the connected operational database. This avoids a file export; results depend on the query and when it runs.

Path 4 · Ask the reporting warehouse

Explore the FHIR reporting source

OpenELIS FHIR → Data Pipes / Spark → Catalyst → Superset

Use the same question, review and dashboard workflow over the FHIR reporting source. The pipeline prepares OpenELIS FHIR data for SQL analysis.

Data: limited to what OpenELIS exports to FHIR and the latest pipeline refresh. Coverage and freshness can differ from the operational database.

Four-pathway videos are in preparation. Partial local checks are available; complete server journeys and owner acceptance remain open. Each pathway will have its own recording here once verified. The applications currently use their existing sign-ins; shared sign-in and equivalent per-user access are separately planned.

Catalyst pipeline

How each query is produced.

Catalyst Gateway owns source context, query versions, optional writer/reviewer composition, advisory findings, and execution. It calls Med Agent Hub only to run configured model roles. The four stages below are the lifecycle shown in both local recordings.

1 Draft

A writer model drafts SQL from the source context supplied by the current runtime.

2 Review

When selected, a reviewer model checks the draft against the same question and schema.

3 Inspect

The person can edit the query and inspect advisory findings without losing the draft.

4 Execute

The exact selected query runs through the configured source and returns rows or its database error.
