Project overview

A framework for orchestrating and evaluating open models in clinical workflows.

Open Clinical AI is an open framework for orchestrating small, open-weight language models against clinical, administrative, and surveillance workflows, and for evaluating the resulting evidence. It combines staged model calls with visible source context, explicit execution, and reviewable results. ChartSearchAI and Catalyst are its example implementations, in OpenMRS and OpenELIS.

Because the models run locally via llama.cpp — no cloud APIs — the same framework fits health systems where connectivity, compute, cost, or data-privacy rules make cloud AI unavailable, without changing the architecture.

Local by design

Runs entirely on local hardware via llama.cpp — no cloud APIs. Patient data never leaves the deployment.

Answer checks

Each product keeps its checks visible: staged model calls, temporal and structure findings, citation resolution, advisory SQL findings, and explicit execution.

Published evidence

Published reports retain the inputs, outputs, source evidence, and review method needed to interpret a result. Catalyst will publish a fresh comparison after its generic connection and Spark reference deployment are accepted.

Med Agent Hub

How each answer is produced.

ChartSearchAI owns the OpenMRS workflow and can execute it through either its bundled provider or a configured Med Agent Hub provider. The recording uses Hub; the five stages below are the shared lifecycle shown in the demo above.

1 Context

Load patient records and source provenance.

2 Answer

Generate the initial answer with the selected profile.

3 Check

Apply deterministic temporal and output rules.

4 Evidence

Resolve citations and record grounding results.

5 In-Depth

Generate additional detail from the checked answer.

Example implementation 2 of 2 · Catalyst

Catalyst: from a question to a dashboard.

The selected Catalyst contract is an analytics and reporting workbench over a configured SQL source. A source declares its dialect and complete readable schema; a person reviews the generated SQL and chooses the exact query to run; successful results can become Datasets, Widgets, and dashboards published to Superset. The recording demonstrates the current runtime end to end: FHIR Data Pipes builds the Parquet warehouse from a FHIR endpoint, Spark SQL serves it, and Catalyst and Superset connect to it as ordinary SQL clients. The generic connection and the OpenMRS HIV Spark reference path are implemented; the model-team comparison has not been rerun against them.

Transcript (silent recording)
  1. The FHIR Data Pipes control panel shows its configured source — an OpenMRS FHIR R4 endpoint — and the settings that write Parquet files and ViewDefinition views.
  2. A pipeline run merges what changed since the last one and names the data-warehouse snapshot it wrote.
  3. The question "How many patients are in this dataset?" is asked against that warehouse; Spark reports twenty-four readable relations, a writer model drafts Spark SQL over them, and a reviewer checks it.
  4. The selected query runs and returns 5,384 patients read from Parquet; the typed result is saved as a Dataset.
  5. A follow-up — "Now break that count down by gender, highest first" — refines the same query, and the counts are saved as a second Dataset.
  6. Two Widgets are built over the saved Datasets and collected into a dashboard, which publishes as a native Superset bundle.
  7. The pinned importer records its receipt, and Superset renders the same numbers from the same Spark source.

Catalyst pipeline

How each query is produced.

Catalyst Gateway owns source context, query versions, optional writer/reviewer composition, advisory findings, and execution. It calls Med Agent Hub only to run configured model roles. The four stages below are the lifecycle shown in the recording.

1 Draft

A writer model drafts SQL from the source context supplied by the current runtime.

2 Review

When selected, a reviewer model checks the draft against the same question and schema.

3 Inspect

The person can edit the query and inspect advisory findings without losing the draft.

4 Execute

The exact selected query runs through the configured source and returns rows or its database error.
